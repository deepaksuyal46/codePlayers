# Deployment — web service + background worker

## Render Blueprint

1. Put the CONTENTS of this extracted root in your development repository, so render.yaml and frontend/ are at repository root. Do not automatically push to the organizer repository; honor your submission commit limit.
2. In Render, create a Blueprint connected to that repository and use render.yaml. Review its service plans/costs before creating services; this package does not promise free worker hosting.
3. Enter MONGODB_URI and MONGODB_DB_NAME matching your working Atlas database. Supply TWOFACTOR_API_KEY. OTP_SECRET is generated by the Blueprint. Set APP_ORIGIN to the exact HTTPS origin of the web service (for example https://your-service.onrender.com, with no path).
4. Allow the hosting service's outbound addresses in the same Atlas project's IP access list. A laptop-only allowlist is not enough for a deployed server. Use a database user with read/write and index-creation access; transactions require a replica set/sharded deployment.
5. After setting the correct APP_ORIGIN, redeploy/restart if required. Both web and worker must be running. Health endpoint: /api/health. This checks database reachability, not live OTP delivery or worker health.
6. From your local configured frontend directory using the SAME Atlas database, run npm run db:check. This also creates required indexes. Run npm run seed only for a catalogue that needs importing. You may instead run these commands in a trusted deployment shell.
7. Register at the deployed site's /login, receive a real SMS OTP, and verify it. Promote that verified account with npm run role:set -- your-email@example.com admin using the same Atlas database. Sign in through Admin Login and verify another OTP.
8. Test customer cart/order flow, admin price/visibility editing, customer denial on /api/admin/stats, and reservation expiry with the worker active.

The frontend directory is a full-stack Next.js deployment. src/backend holds OTP services, src/database holds auth schemas, src/lib holds shared database/commerce code, and src/app/api is the backend HTTP entry point. No second frontend or separate Express server is needed.

## Docker / other container hosts

The frontend/Dockerfile builds and starts the Next.js server. Configure the same environment values at runtime, not as build arguments. Launch a second container from the same image with command `npm run worker`.

For a host with Docker Compose, set frontend/.env.local then run from root:

```sh
docker compose up --build -d
```

The production cookie requires HTTPS. Put the web service behind an HTTPS reverse proxy and set APP_ORIGIN to that public HTTPS origin. For ordinary localhost testing use npm run dev, not the production Docker setup over plain HTTP. Compose exposes port 3000; restrict its public exposure behind your proxy/firewall.

## Vercel

Next.js can be hosted with frontend as the project root and the same environment variables. The persistent expiry worker cannot run as an endless Vercel function; deploy the worker separately on an always-on Node/container service using the same database. This package does not include a scheduled-function replacement. Avoid calling the whole deployment complete until the worker is running.

## 2Factor account requirements

This package targets **2Factor.in SMS OTP**, using the documented custom-code POST endpoint:
https://2factor.in/API/V1/{api_key}/SMS/{phone_number}/{otp_code}

The server generates and verifies the code locally with an HMAC; the provider delivers it. No guessed email API or provider verification URL is needed. Indian mobile numbers only; the app normalizes them to 91 + 10 digits. A provider API success does not guarantee delivery to every handset. Your account must have the appropriate service enabled, sufficient credits and any required approved template/sender configuration. TWOFACTOR_TEMPLATE is optional; set it only if your account's documented custom-code API supports/requires a named template suffix. No SMS is sent by the test suite.

If you actually have a different provider at twofactor.com, compare its API documentation before use; an API key from another service is not interchangeable with 2Factor.in.

## Important operational behavior

- Resend keeps the same expiry deadline and attempt count. After five minutes or five incorrect guesses, start again.
- Provider timeouts fail closed; the UI gives a generic error. No OTP is printed to logs as a fallback.
- Account creation, cart creation and code consumption occur in one MongoDB transaction. If a process crashes during verification, start again after expiration.
- SMS send limits are stored in MongoDB: five requests per phone/email per fixed hour and 100 globally per fixed hour, plus a per-phone minute bucket. Resending also has an exact 60-second challenge cooldown. These are hackathon defaults, not an anti-fraud service; configure gateway/provider spending limits and edge request limits before wider public traffic.
- Keep the OTP_SECRET stable across web instances. Rotating it invalidates outstanding codes.
- Do not configure request tracing to capture the 2Factor request URL: the provider's API format includes its key and OTP in the path.
- No real gateway payments, password recovery, or phone-number recovery are implemented.
